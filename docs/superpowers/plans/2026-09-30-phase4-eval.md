# Phase 4 planted-case eval — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `npm run eval` builds planted same-order / new-order cases from clean real invoices, asks Jev, tunes the threshold on `tune` and reports on `test`.

**Architecture:** Two pure modules (`plant.ts` builds cases and their Jev states; `metrics.ts` scores them) and a CLI (`run.ts`) that wires Phase 1 routes, Phase 2 features and Phase 3's cached asker together.

**Tech Stack:** TypeScript (ESM, `tsx`), Vitest, `@typesafe-ai/sdk` via Phase 3's `createAsker`.

**Spec:** docs/superpowers/specs/2026-09-30-phase4-eval-design.md

## Global Constraints

- No network and no data/raw in tests. No paid Jev call without the user's go-ahead.
- `demo` is never a source of planted cases and never appears in a report.
- The states are Phase 3's `stateFor` output: no ids, names or cities.
- Nothing is committed unless the user asks; out/ stays local; paths in output go through `displayPath`.
- Seeded and deterministic: the same seed gives the same cases.

## Review Focus

1. Not enough candidates for `--per-label` in a split → a clear error naming the split, kind and counts (plant test).
2. A shifted date that crosses a split or year boundary → the case is skipped, never mislabelled (plant test).
3. `out/jev.json` missing, or from a different model → the real-load section is skipped or a warning is printed; the run doesn't crash (run.ts, manual dry check).
4. All tune positives with an identical p (ties) → `chooseThreshold` still returns a threshold that meets the target (metrics test).
5. An invoice with a product on two lines → the split and rebill subsets work on lines, and the totals still equal the sum of the lines (plant test).

### Task 2: `src/eval/metrics.ts`

**Produces:**
```ts
export interface Scored { p: number; positive: boolean }
export function auc(xs: readonly Scored[]): number | null;           // ties ½; null without both classes
export function wilson(k: number, n: number): { low: number; high: number } | null; // 95%; null if n = 0
export interface Confusion { positives: number; negatives: number; flagged_positives: number; flagged_negatives: number;
  recall: number | null; recall_ci: {low:number;high:number} | null; false_alarm_rate: number | null; false_alarm_ci: {low:number;high:number} | null }
export function confusionAt(xs: readonly Scored[], threshold: number): Confusion; // flagged = p ≥ threshold
export function chooseThreshold(xs: readonly Scored[], targetRecall: number): number; // k-th largest positive p, k = ceil(target·nPos)
```

- [ ] Tests first (`src/eval/metrics.test.ts`): AUC = 1 when perfectly separated, 0 inverted, 0.5 when all tied, null for one class;
      Wilson(0,10).low = 0 and (5,10) ≈ {0.2366, 0.7634}; `p = t` is flagged; chooseThreshold on positives [0.9,0.8,0.7,0.6,0.5]
      with target 0.8 → 0.6, and with ties [0.4,0.4,0.4] → 0.4; recall at the chosen threshold ≥ target; throws without positives.
- [ ] Implement; tests pass.

### Task 3: `src/eval/plant.ts`

**Consumes:** `featuresFor` (Phase 2), `stateFor`/`JevState` (Phase 3), `lineSignature`, `compareInvoiceNumbers`, `addDays`, `daysBetween`, `DUPLICATE_LINES_DAYS`.

**Produces:**
```ts
export type CaseKind = "split" | "rebill" | "moved";
export type CaseLabel = "same_order" | "new_order";
export const LABEL: Record<CaseKind, CaseLabel>;
export type EvalSplit = Exclude<Split, "demo">;
export const EVAL_SPLITS: readonly EvalSplit[]; // ["tune", "test"]
export function splitOfDate(isoDate: string): Split; // same boundaries as SPLIT_SQL
export function mulberry32(seed: number): () => number;
export interface PlantedCase { case_id: string; kind: CaseKind; label: CaseLabel; split: EvalSplit; source_invoices: string[];
  gap_days: number; previous: InvoiceBundle; current: InvoiceBundle; features: Features; state: JevState }
export interface PlantInput { bundles: readonly InvoiceBundle[]; routes: ReadonlyMap<string, Route>; fromPendingDelivery: ReadonlyMap<string, boolean> }
export interface PlantOptions { perLabel: number; seed: number; gapWeights: ReadonlyMap<number, number> }
export function plantCases(input: PlantInput, options: PlantOptions): PlantedCase[];
```

Algorithm: see the spec. Per split, one PRNG `mulberry32(seed * 1000 + splitIndex)`; shuffle the candidates (Fisher–Yates);
take `moved` pairs first, then positives: while `split` needs more, make a split; then rebills. A candidate that fails a check is
skipped. A built invoice gets `invoice_number = source + "-a" | "-b" | "-r" | "-m"`, lines renumbered from 1 with the new
billing date, totals and commission recomputed, `installments: []`, `split = splitOfDate(date)`; its from_pending_delivery
copies the source's value into a local copy of the map.

- [ ] Tests first (`src/eval/plant.test.ts`), with fixture customers built from `bundle()` (dates in 2025, clean routes):
      labels by kind; counts per split = perLabel per label (⌈N/2⌉ split, ⌊N/2⌋ rebill); split: previous ∪ current lines = X's
      lines (as product×qty multisets), both non-empty, totals = Σ line amounts, and the invoice has a product on two lines;
      rebill: current is a strict subset, previous is X; moved: current has N's lines at P's date + gap; gap ∈ gapWeights keys;
      no source reused; demo invoices never used; a date shift that would cross 2026-01-01 isn't used; a pair with the same
      signature isn't a moved case; the same seed gives the same case ids and states; a different seed gives different ones;
      too few candidates → an error naming the split; state keys contain no id-like key.
- [ ] Implement; tests pass; typecheck passes.
